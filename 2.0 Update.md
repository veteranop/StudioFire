## 1. Reports (AGREED, pending one open item)

### 1.1 Station context
- KDPI is **non-commercial**. "Spots" are underwriting, PSAs, promos and station IDs, never ads.
- KDPI **streams online via StreamGuys**, so SoundExchange webcasting reporting applies on top of terrestrial performing-rights reporting.
- Which licensing bodies the station reports to, and how often, is **unknown**. See §1.6.
- Reports are **on screen only** for 2.0. Every report has a CSV export and a printable view. No email delivery yet.

### 1.2 What exists today (v1.5.0)
- One report: an as-aired log for a date range, filtered to all, music only, or spots only, with CSV export (`services/core/app.py` `_report_rows`, `web/templates/reports.html`).
- The source data is `play_history`, ingested from the P1 journal. `track_start` rows carry only `ts`, `path`, `title` and `source` (`playlist|show|manual|spot|emergency|baked_in`).
- The journal also logs `track_end` (reason eof/error), `track_skip`, `crossfade`, `emergency_enter/exit`, `mpv_restart`, `pause/resume` and `engine_start/stop`. No report uses these yet.

### 1.3 Data foundation (build first; all priority reports depend on it)
| Gap | Why it matters | Change |
|---|---|---|
| Spots log only `source='spot'` | IDs, underwriting, PSAs and promos can't be told apart, so there is no per-sponsor proof. | New `spot_rules` columns: `category` (`id`, `underwriting`, `psa`, `promo`, `jingle`) and `sponsor` (free text, required when the category is underwriting). The spot editor gets fields for both. On `track_start`, P1 logs `rule_id`, `category` and `sponsor`, which Core passes in the queue entry. |
| No artist/album in the play log | Joining `tracks` by path breaks when files move or get renamed. | Snapshot `artist`, `album` and `duration_sec` into the queue entry when it is fed. P1 echoes them into `track_start`. |
| No actual played duration | Airtime differs from file length because of crossfades and skips. | At ingest, pair each `track_start` with the next `track_start`, `track_end` or `crossfade` boundary and store `played_sec`. |
| No expected count for spots | An affidavit needs "scheduled N, aired M". | Compute expected airings from `spot_rules` triggers (interval/clock/daily/weekly/once) over the range. |

Schema: new migration adding `play_history` columns `artist`, `album`, `category`, `sponsor`, `rule_id` and `played_sec`, plus the `spot_rules` columns above.
- Older rows keep NULLs. Reports show "uncategorized spot" for those and never guess.
- P1 stays stdlib-only. It just copies the extra fields from the queue entry into the journal line.

### 1.4 Priority reports for 2.0 (in build order)

**R1. Legal ID compliance**
- For each clock hour in the range: PASS if a `category='id'` spot aired inside the window, otherwise MISSED.
- The window is configurable in Settings (default :55 to :05 around the top of the hour).
- Output: a summary (X of Y hours compliant), then a table of missed hours first, then every hour with the ID's air time.
- Hours spent in emergency mode are flagged separately as "off-automation", with the reason.

**R2. Underwriting affidavit**
- Filters: sponsor (dropdown of distinct sponsors) and date range.
- Output: sponsor name, the range, scheduled vs aired count, and every airing with its timestamp and the spot file played.
- The printable view is a clean page with the station name and generation date, suitable to hand to the underwriter.
- Also offer an all-sponsors summary table: sponsor, scheduled, aired, delivery %.

**R3. Problem tracks / library health**
- Plays that failed: `track_end` with `reason=error` (decode errors) and `track_skip`, with the reason and count.
- Library issues: tracks with `missing=1` (the file is gone), tracks with no `duration_sec` (feeds §3), and tracks missing a title or artist tag.
- Each row shows the path and the last time it aired or was queued. The count is grouped by issue type.
- Read-only in 2.0. It links to the existing duplicates/cleanup tools where they apply.

### 1.5 Backlog (not in 2.0; kept for later)
- Music licensing log for BMI/ASCAP/SESAC sample periods (blocked on §1.6).
- Rotation / over-rotation, separation violations, dusty library, hour-by-hour clock, show log, genre/era mix (needs §2), on-air reliability / uptime.
- Weekly email summary.

  - If StreamGuys gets audio only (Barix → StreamGuys), any SoundExchange report StreamGuys produces would have no song data.
  - Listeners' players would also show no song title.
- Action for Mark: ask StreamGuys (a) whether they file or prepare SoundExchange reports for KDPI, and (b) how they take now-playing metadata (HTTP metadata endpoint, Icecast admin `metadata` call, or similar).
- Action for Mark: ask John or the station manager which performing-rights bodies KDPI is licensed with and whether it gets census/sample-period requests.
- Candidate 2.0 feature, depending on the answer: P2 pushes the current title and artist to StreamGuys on every `track_start`. It must be fire-and-forget and must never sit in the audio path.

## 2. Music Intelligence (AGREED)

### 2.1 Goals
- **Uniform genres** from an established vocabulary, assigned mostly **per artist**, with album and track overrides where an artist crosses genres. Example: Bob Marley → Reggae for every track; no per-song tagging needed.
- The genre list and the assignments must stay **editable** by station staff after 2.0 ships.
- **Popularity from national/global data.** KDPI has no chart data today.
- Support **"under the radar" programming**: deep cuts and B-sides by well-known artists.
- All of it **searchable** in the library and usable by the playlist generator (§4) and reports.

### 2.2 Topology: enrich once, centrally; consume everywhere
- KDPI runs StudioFire on **two PCs**: the playout PC and a production PC. Today each has its own local SQLite index of the NAS.
- **SQLite must not be shared live over SMB.** File locking and WAL are unreliable on network shares, and that risks corrupting the database.
- Design:
  - **Enrichment runs only on the production PC.** It is a new mode of the P3 worker, enabled by a config flag (`"enrichment": {"enabled": true}`), and is off by default. The playout PC never makes internet lookups.
  - The production PC publishes a **catalog snapshot** to the NAS, for example `\\KDPI-Media\music\.studiofire\catalog.sqlite`. It writes `catalog.tmp`, then renames it, so readers never see a half-written file. It also writes `catalog.json` with the version number and timestamp.
  - Every StudioFire instance (the playout PC included) checks the snapshot version periodically (default hourly). When it changes, the instance **copies the file locally** and merges it into its own DB. The merge is read-only with respect to the NAS.
  - If the NAS or the snapshot is unavailable, the instance keeps its last merged metadata. **Playout never depends on the catalog.**
- **Keying:** catalog rows are keyed by a **NAS-relative path** (relative to `nas_music_root`, so Z:/UNC/alias differences don't matter). They also store a content fingerprint (size + duration, plus the AcoustID fingerprint when available), so moved or renamed files can be re-matched.
- **Tags in the audio files are not modified** in 2.0. Writing to a 4TB library is risky and changes mtimes, which forces a full re-index. ID3 write-back is a possible later option.

### 2.3 Data sources (all free; all cached; all rate-limited)
| Source | Used for | Notes |
|---|---|---|
| Existing file tags (genre, year, ISRC) | First-pass genre/year | The indexer currently ignores genre and year. Add them. |
| MusicBrainz | Canonical artist/recording/release IDs, release year, ISRC, artist genres, track length (feeds §3) | Max 1 request/sec. Custom User-Agent required. |
| AcoustID (+ Chromaprint `fpcalc`) | Identifying a recording when tags are missing or junk | Free API key. KDPI is non-commercial, so the free tier applies. |
| Last.fm | Community tags (style hints); **listeners/playcount**; `artist.getTopTracks` (artist's hits, ranked) | Free API key. |
| Deezer | Track `rank`, a second popularity signal | No key needed. |

Excluded: Spotify (restrictive terms; audio features removed in 2024) and scraped chart sites (Billboard: no free API, and scraping breaks their terms).

### 2.4 Genre model
- **Two levels:**
  - **Genre:** a short station list of well-established top-level genres.
  - **Style:** optional finer tags drawn from the MusicBrainz genre vocabulary (e.g. "outlaw country", "roots reggae").
- **Seed list:**
  - Ship a default list of about 20 established top-level genres, as a migration/seed.
  - Base it on standard top-level categories (MusicBrainz and Discogs top-level genres, adjusted for radio: keep Country, Folk, Americana and Bluegrass separate, for example).
  - The station edits the list after install. Nothing is hard-coded outside the seed.
- **Artists:** each artist has a **primary genre** and an optional **secondary genre**.
- **Albums:** an album can **add** genres on top of its artist's genres, for crossover records. It can also set a different primary genre for that album.
- **Tracks:** a track override exists for rare exceptions. It can also add genres or replace the primary.
- **Resolution:**
  - A track's **primary genre** is the track primary if set, else the album primary, else the artist primary, else unassigned. Reports count by primary genre.
  - A track's **genre set** is the artist primary + secondary, plus album-added genres, plus track-added genres. Search and the playlist generator match on the whole genre set.
- **Automatic assignment:**
  1. Collect raw tags (file tag, MusicBrainz artist genres, Last.fm top tags).
  2. Map them through an editable **raw-tag → station-genre mapping table** (`genre_map`).
  3. Take the top-weighted genre as the artist's primary and the second as its secondary, but only if its weight passes a configurable threshold.
  4. Store a confidence score. Low-confidence artists go to a **Review queue** instead of being assigned silently.
- **Human decisions win.** Any genre set or edited by a person is `locked` and is never overwritten by later enrichment runs.
- **Admin "Genres" page:**
  - Add, rename and merge genres. A merge re-points all assignments.
  - Edit `genre_map`.
  - Bulk-assign by artist.
  - Work the review queue.
  - Add album crossover genres and set track overrides.

### 2.5 Popularity model
- **Artist popularity** (0–100): Last.fm listeners, log-normalized across the library.
- **Track popularity** (0–100): a blend of Last.fm track listeners and Deezer rank.
- **Track rank within its artist:** its position in Last.fm `artist.getTopTracks`.
- **Tier**, derived and used for search, reports and the generator:
  - **Hit:** the artist's top ~5 tracks, or track popularity above the threshold.
  - **Known:** everything between Hit and Deep cut.
  - **Deep cut:** an artist with medium-to-high popularity, a track outside the artist's top ~25, or no match in the top tracks.
  - **Unknown:** no data, e.g. local or obscure artists. Never treated as low quality; just unscored.
- Popularity is refreshed on a slow cycle (e.g. every 90 days per track). Thresholds are configurable.

### 2.6 New data (catalog schema, sketch)
- `artists`: name, normalized name, MusicBrainz ID, `primary_genre_id`, `secondary_genre_id`, `genre_locked`, popularity, confidence.
- `albums`: artist, title, MusicBrainz ID, year, `primary_genre_id` (nullable override), `locked`.
- `album_genres`: album → additional genre (many-to-many).
- `track_meta`: relative path, fingerprint, MusicBrainz recording ID, ISRC, year, `primary_genre_id` (nullable override), `locked`, popularity, artist rank, tier, `enriched_at`.
- `track_genres`: track → additional genre (many-to-many).
- `styles` and `track_styles` / `artist_styles`: the finer style tags.
- `genres`: the station list. `genre_map`: raw tag → genre.

### 2.7 Search and UI
- Library search gains filters for genre, style, decade/year, tier and popularity range.
- The playlist editor shows a genre chip and tier on each item.
- The report backlog gains genre mix and hits-vs-deep-cuts share.

### 2.8 Decisions log
- One primary genre and an optional secondary per artist. Albums can add crossover genres. (Mark, agreed)
- Popularity uses national/global data (Last.fm + Deezer), and deep cuts are a first-class tier. (Mark, agreed)
- Enrichment runs only on the production PC. The catalog is shared through a NAS snapshot, never a live shared DB. (Mark, agreed)

## 3. Missing Durations (AGREED)

### 3.0 Scope and first step
- Scope is **song length only**. No intro, outro or cue markers. (Mark, agreed)
- Unknown lengths are **widespread across ordinary library songs**, not just shows. Treat this as a library-wide fix.
- **Step 1 is a diagnostic, before building anything.** Add a one-off script (`scripts/duration_audit.py`, read-only) that reports counts of unknown or zero lengths in `tracks`, broken down by:
  - `tags_read` state (not yet read vs read but no length);
  - `duration_sec` NULL vs `0.0`;
  - file extension, and top-level folder;
  - `missing` flag.

  Mark runs it on the playout PC's DB. The numbers decide which of the causes in §3.1 dominates, and so the order the fixes in §3.2 are built. Expect "phase 2 backlog" and "0.0 stored as known" to be the big ones. Those are the cheapest fixes.

### 3.1 Why durations are missing today (from reading v1.5.0)
- **Indexer phase 2 backlog.** New files get a path-only row (`tags_read=0`). The duration arrives only when the throttled tag pass reaches the file, and on a 4TB library that can lag a long way.
- **Unreadable headers → 0, not NULL.**
  - `read_tags()` stores `round(length or 0.0)`, so a file mutagen can't measure gets `duration_sec = 0.0`.
  - `item_durations()` uses `COALESCE(i.duration_sec, t.duration_sec)`. A 0.0 from `tracks` may therefore be treated as known. Verify this, and treat `<= 0` as unknown everywhere.
- **VBR MP3s without a Xing/VBRI header.** Mutagen estimates the length from the bitrate and can be badly wrong, not just missing.
- **Files outside `nas_music_root`** (DJ folders, show files, spots referenced by `.lst` or schedules) are never indexed. They get a length only when added singly (`probe_duration`) or when first fed to air.
- **Learned lengths aren't shared.** The feeder learns a real length when it caches a song for air, but `set_duration_if_unknown()` writes it only to that one `playlist_items` row. The `tracks` table, other playlists and the other PC never get it.
- **Zara `.lst` imports.** Garbage or negative durations (e.g. `-2`) become NULL. That's correct, but nothing back-fills them.
- **Formats not in `AUDIO_EXTS`** (e.g. `.wma`, `.aif/.aiff`, `.opus`) are never indexed. Check the NAS for these.

### 3.2 Fix: a duration pipeline with provenance
Store **where each duration came from**, so better sources can replace worse ones and a human can see why a value is trusted.

- New `tracks` columns: `duration_source` (`header`, `decoded`, `measured_air`, `musicbrainz`, `lst`, `manual`) and `duration_checked_at`.
- **Trust order** (higher replaces lower; never the reverse): `manual` > `decoded` ≈ `measured_air` > `header` > `musicbrainz` > `lst`.
- **Normalize unknown:** `NULL` means unknown everywhere, and `0` or negative values are never stored. A migration converts existing `0.0` values to `NULL`.

**Sources, cheapest first:**
1. **Header read (mutagen):** as today, but it marks `duration_source='header'`. It flags VBR MP3s without a Xing/VBRI header as **suspect**.
2. **Decode measurement:** for unknown or suspect files, measure the true length by decoding.
   - Use mpv, already a dependency, or a bundled `ffprobe`/`ffmpeg`. Pick one and document the choice.
   - This is heavy, so it runs on the **production PC** in the enrichment worker (§2.2), throttled. The results ship to the playout PC in the catalog snapshot.
   - The playout PC never bulk-decodes over SMB.
3. **Measured on air:** when P1 plays a track start-to-EOF (`track_start` → `track_end reason=eof`, no skip/crossfade cut), Core records the measured length back to **`tracks`**, not only to the playlist item.
   - Use it to confirm or correct the header value.
   - Measurements on a crossfade-cut play are discarded.
4. **MusicBrainz recording length** (from §2): a cross-check only. It's a different master or edit for many files, so it never overrides a decoded or measured value. Flag a mismatch over 10 seconds for review.
5. **Write-back everywhere:**
   - Any newly learned duration updates `tracks` and fills NULL `playlist_items.duration_sec` for the same path.
   - The next `.lst` save then writes correct milliseconds back for Zara.

### 3.3 Coverage beyond the music root
- Index **referenced paths** too: any file used by a playlist, `.lst`, schedule or spot rule that lives outside `nas_music_root`. Give these a `referenced=1` flag. Durations are read on the production PC as above.
- Add the missing extensions to `AUDIO_EXTS` (`.wma`, `.aif`, `.aiff`, `.opus`) if mpv plays them on the playout PC. Verify on Windows first.

### 3.4 Visibility
- R3 (Problem tracks / library health, §1.4) shows unknown, suspect and mismatched durations, grouped by folder and format.
- It includes a one-click "measure now" action, queued to the production PC.
- The playlist editor's existing run-time display shows "≈" when any item's length is estimated, and "?" with a count when any is unknown.

## 4. Automated Playlist Generator (AGREED)

### 4.1 Depends on
- §2 for genre, tier and popularity.
- §3 for durations. A track with an unknown length is **never** used by the generator.
- `play_history` for recency rules.

### 4.2 Inputs (a saved "recipe"; recipes can be named and reused)
- **Target run time**, e.g. 60 min or 3 h, with a tolerance (default ±2 min).
- **Genre mix**: one or more genres with weights (e.g. Blues 60%, Americana 40%). Matches on the track's genre set (§2.4).
- **Popularity mix** by tier (e.g. Hits 30%, Known 40%, Deep cuts 30%). Option to include or exclude Unknown-tier (local/unscored) tracks, with a %.
- **Era** (optional): a decade or year range.
- **Randomization**: a 0–100 slider.
  - 0 = strictly the best matches by popularity score.
  - 100 = uniform random within the filters.
  - Implemented as weighted random sampling with the slider as the temperature.
  - A **seed** is stored with each generated playlist so it can be reproduced.
- **Rules**: see §4.6. Station defaults are set in Settings and can be overridden per recipe.

### 4.3 Algorithm (sketch)
1. Build the candidate pool from the recipe filters plus every `filter` rule (§4.6).
2. Split the target time into genre and tier quotas, measured in minutes, not song counts.
3. Fill greedily by weighted random draw, checking every `constraint` rule (§4.6). When a draw violates a rule, redraw. After K failures (default 50), relax the soft rule with the lowest `relax_order` by one step, and record that in the generation notes.
4. **Time-fit pass:** once within ~8 minutes of the target, pick the songs whose lengths best close the gap within tolerance (small subset-sum over the remaining candidates).
5. Order the result so genres and tiers are spread out rather than clumped, while keeping artist separation.
6. Show the generation notes: actual vs target time, actual vs requested mix, and any rules relaxed.

### 4.4 Output and workflow
- The generator **produces a normal playlist**, saved as a `.lst` like every other playlist (migration 10 behavior). John reviews and edits it in the existing editor, then schedules it with the existing scheduler. **Nothing generated goes to air without passing through a normal playlist.**
- UI: a "Generate" button on the Playlists page opens the recipe form, then shows a preview with time and mix stats. Buttons: Regenerate (new seed), Save as playlist, or Save recipe.
- **No auto mode in 2.0.** There is no unattended regenerate-on-schedule. (Mark, agreed)

### 4.5 Run time and the schedule
- **Target run time counts music only.** Spot-rule insertion is unchanged: spots still go in at song boundaries during air, and the generator does not reserve time for them. (Mark, agreed)
- **Hard end times are already handled by the scheduler. Do not add show-end logic to the generator.**
  - `engine_bridge._maybe_fire_scheduled()` already lets a scheduled show take over a running show (`_finish_show` then `_start_show`), interrupting at the next song boundary.
  - A generated playlist that overruns is cut when the next scheduled item fires, exactly like any other playlist.
  - Known behavior to keep in mind: takeover happens at the **song boundary**, so the next show can start up to one song late. That is unchanged in 2.0.
- Tolerance stays at the default ±2 min (configurable per recipe).

### 4.6 Rules: built to be extended, documented in one place
Mark expects to add rules over time. So rules are **not** scattered through the algorithm.

- **One module**, e.g. `services/core/generator_rules.py`. Each rule is a small, self-contained object registered in a `RULES` list:
  - `id`, e.g. `artist_separation`.
  - `label` and a plain-English `description`, shown in the UI and the generation notes.
  - `kind`: `filter` (removes candidates from the pool before drawing) or `constraint` (checked against the playlist built so far).
  - `hard` (never relaxed) vs `soft`, with a `relax_order` (soft rules relax lowest-first when the generator gets stuck) and a `relax()` step (e.g. 60 → 45 → 30 min).
  - `params` with defaults. Defaults live in Settings; recipes may override.
  - `check(candidate, context) -> (ok, reason)`. Pure functions, no DB writes, so every rule is unit-testable in isolation.
- **Adding a rule** means writing one class, adding it to `RULES`, and adding one test. No changes to the core algorithm.
- **Starting rule set (defaults):**

| id | kind | hard/soft | default | meaning |
|---|---|---|---|---|
| `exclude_unplayable` | filter | hard | n/a | No `missing=1`, unknown/zero duration, or R3 decode-error tracks |
| `no_dup_in_playlist` | constraint | hard | n/a | A track appears at most once per generated playlist |
| `track_recency` | filter | soft | 3 days | Skip tracks that aired within N days (from `play_history`) |
| `artist_separation` | constraint | soft | 60 min | Same artist not within N minutes of playlist time |

- **Generation notes** list every rule that filtered or blocked candidates, how many tracks each rejected, and any relaxations. That way John can see *why* a playlist looks the way it does.
- **Documentation:**
  - Write `docs/Playlist-Generator.md` with the recipe fields, the algorithm steps (§4.3), every rule with its defaults and relax behavior, and a "How to add a rule" walkthrough. Link it from `docs/Home.md`.
  - Keep the module docstring and that doc in sync. Any PR adding a rule updates both.

### 4.7 Decisions log
- A reviewed, saved playlist is the output. There is no auto mode in 2.0.
- The run-time target counts music only. Spot insertion logic is unchanged.
- Show cut-off is the existing scheduler takeover. The generator doesn't handle it.
- The starting rules are 60-min artist separation and a 3-day track no-repeat, and the rule set is expected to grow.

## 6. Release Safety: Major Version Gate, Indexing and Databases (AGREED)

### 6.1 How updates reach the station today (v1.5.0, verified)
- `services/updater.py` installs **published GitHub Releases only** (`/releases/latest`, or `--tag`). Branches and unreleased commits never reach a station.
- `scripts/release.py` publishes **only from `main`** (clean tree, in sync with origin, tests pass). There is no CI that publishes.
- The Settings page offers "Install update" whenever `latest > current`. **It has no notion of major versions.** If v2.0.0 were published today, every 1.x box would offer it behind the same everyday button.
- The updater **refuses a release whose `requirements.txt` changed** (that needs the full installer). It **never touches `bin/`** (mpv, nssm, so a new `fpcalc` binary can't ship this way) or `data/`.
- **Rollback restores the code only, not the database.** If an update migrates the DB and then fails its health check, the restored old code runs against the migrated DB.

### 6.2 Branching rules (start now)
- All 2.0 work happens on the long-lived branch **`v2-dev`**. This planning doc lives on `planning/2.0` until then.
- `main` stays the 1.x production line. 1.x hotfixes still release from `main` as usual.
- **Do not merge `v2-dev` into `main` until §6.3's gate has shipped to stations in a 1.x release and been confirmed installed.** Merging early means the next 1.x hotfix release would carry 2.0 code.
- Never run `scripts/release.py` with a 2.x version until §6.3 and §6.4 are complete.

### 6.3 "Major Version Update" gate (ships FIRST, in a 1.x release, e.g. v1.6.0)
The gate must already be on the stations *before* 2.0 is published, because the code that decides what to offer is the installed 1.x code.

- **Updater check:** list releases (`/releases`) instead of `/releases/latest`. Return two things:
  - `update_available`: the newest release **within the current major** (1.x → 1.y). This feeds the existing everyday "Install update" button, unchanged.
  - `major_available`: the newest release with a **higher major**. It never feeds the everyday button.
- `apply()` without `--tag` must **never cross a major version**. `apply --tag v2.x` also requires a new explicit flag, `--major`. Defense in depth: even a scripted or accidental call can't cross a major version.
- **Settings UI**, in a separate card below Software updates:
  - It has a distinct style (amber or red border) and the title **"Major Version Update available: 2.0"**.
  - It shows the release notes and a short "what changes / what to expect" summary (a `MAJOR.md` attached to the release, or the notes body).
  - **Admin role only.** Operators see that a major version exists but get no button.
  - To install, the admin must **type the version** (e.g. `2.0`) into a box. The button stays disabled until it matches. Then a final in-page confirm step. No single-click path.
  - Before enabling the button, it runs a **pre-flight** and shows the results:
    - enough free disk space for the backups;
    - a DB integrity check (`PRAGMA integrity_check`);
    - the engine not in emergency mode;
    - a recommendation not to start it within 10 minutes of a scheduled show.
- **Major updates are never automatic**, and nothing schedules them.
- Tests: within-major vs cross-major selection; `apply` refuses to cross a major version without `--major`; the UI endpoint enforces admin and the typed confirmation server-side, not just in the browser.

### 6.4 Database safety
- **Where each database lives (no others):**

| File | Where | What | Notes |
|---|---|---|---|
| `data/studiofire.db` | every PC | existing app DB (library index, playlists, history…) | unchanged location |
| `data/catalog.sqlite` | every PC | local copy of the published catalog (§2.2) | replaced atomically. `ATTACH`ed **read-only** by Core/worker. Delete it and it is re-fetched. Never written in place. |
| `data/enrichment.sqlite` | production PC only | lookup cache (MusicBrainz/AcoustID/Last.fm/Deezer responses), work queue, rate-limit state | created only when `enrichment.enabled` is true |
| `<catalog.publish_dir>/catalog.sqlite` + `catalog.json` | NAS | the published snapshot | written by the production PC only. `publish_dir` comes from config, default `\\KDPI-Media\music\.studiofire`, which must be **outside `nas_music_root`** or skipped by the indexer (see §6.5). |

- All paths are resolved through the existing `data_dir()` / config helpers. Nothing is hard-coded and nothing is relative to the CWD. Directories are created with `os.makedirs(..., exist_ok=True)` at first use.
- **Catalog edits (genre locks, overrides, mapping) happen only on the production PC**, the catalog's source of truth. On other PCs, the Genres page is **read-only** and says where to edit. Otherwise edits would be overwritten by the next snapshot.
- **Migrations are additive only** (`CREATE TABLE`, `ADD COLUMN`, `CREATE INDEX`). No rebuilding or dropping of existing tables in 2.0, so a code rollback to 1.x still runs on a migrated DB. 1.x's `migrate()` already skips unknown higher versions. Verify that 1.x code tolerates the new columns and tables.
- **Pre-migration backup:** before applying any migration, `migrate()` writes `data/backups/pre-migration-v<old>-to-v<new>-<stamp>.db` with the SQLite backup API and runs `PRAGMA integrity_check`. It aborts (and does not migrate) if either fails. Keep the last 5.
- **Major-update rollback also restores the DB:** for a cross-major install, if the health check fails, restore `studiofire.db` from the update's backup as well as the code. The everyday 1.x path stays as is.
- Test every new migration against **a copy of the real station DB** (Mark supplies one, read-only), as well as an empty DB. Assert row counts in `tracks`, `playlists`, `playlist_items`, `play_history` and `spot_rules` are unchanged afterwards.

### 6.5 Indexing safety (the indexer runs on the on-air PC)
- **No full re-tag.** Adding genre/year/ISRC to `read_tags()` must **not** reset `tags_read` for 4TB of files.
  - Add a separate `tags_version` column (default 1).
  - A low-priority background pass re-reads old rows to the new version, using the existing throttle, after normal indexing is caught up.
  - Search and playout keep working the whole time.
- New/changed-file detection (path, mtime, size) stays exactly as is. Nothing in 2.0 may cause unchanged files to be treated as changed.
- **The indexer must skip the `.studiofire` folder** (and dot-folders generally) if `publish_dir` is anywhere under the music root.
- Decode measurement (§3.2) and all internet lookups run **only on the production PC**, never in the on-air PC's indexer.
- `missing=1` handling and path-alias behavior (the 1.x KDPI path fixes) must not regress. Re-run `tests/test_indexer.py` and add cases for `tags_version` and the folder skip.
- Ship the indexer changes behind a config flag, on by default only after Mark has run them on the production PC against the real NAS.

### 6.6 Dependency rule
- Prefer stdlib (`urllib`, `json`, `sqlite3`) plus the existing `mutagen` for all 2.0 lookups, so `requirements.txt` stays unchanged.
- If a new package or a `bin/` binary (e.g. `fpcalc` for AcoustID) is truly required, 2.0 ships via the **full installer**, and the major-version notes must say so. Keep `fpcalc` optional: production PC only, and enrichment degrades to tag/text matching without it.
