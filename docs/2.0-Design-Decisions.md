# StudioFire 2.0 — Design Decisions

The 2.0 program **as decided**. This is the durable record of *what* and *why*;
the working spec is `2.0-Update.md` (handoff), and the independent review lives
in `.hermes/claude-handoff/studiofire2-plan-review-2026-10-05/`. Build happens on
branch `v2-dev` — see [[StudioFire/docs/Release-and-Branches|Release & Branches]].

> **Status discipline:** only decisions marked AGREED here are committed. The
> ground rules below (P1 stdlib-only, additive migrations, NULL-safe reports,
> tests alongside each feature) are binding on every 2.0 change.

## Vision

2.0 turns StudioFire from "never goes silent" into "can prove what it aired and
program itself intelligently" — **without** adding a network dependency to the
audio path. Four themes: **compliance reports**, a **music-identity** layer
(genre / popularity / searchable metadata), **fixing missing durations**, and an
**automated, human-reviewed playlist generator**.

## The locked consensus (merged 8.7)

Independent critical review by Rosie (research) and Elon (adjudication), then a
cross-review round. Ticket **M2627805 (#720)**.

- The vision is right. **§6 release safety is the strongest part — ship it
  untouched.**
- The risk is **product mass, not correctness**: the full music-intelligence
  layer is "a second product inside the first," and the plan under-owned the
  compliance-export surface that matters most for a non-commercial stream.
- **The single biggest change: cut an explicit 2.0.0 MVP spine** and stage the
  full enrichment layer to 2.0.x / 2.1. The generator must **not** block on full
  enrichment — tags + categories + manual assignment bridge it early.
- This consensus governs **sequence and emphasis only.** It overturns no AGREED
  decision: §6, the NAS-snapshot catalog topology, the duration plan, the
  generator rules model, and the P1 stdlib-only law all stand as written.

## The 2.0.0 MVP spine (build order)

Each step ships as its own release on `v2-dev` (`2.0.0-alphaN`), **except step 0
which ships on the 1.x line from `main`**. Full test suite + DEPLOY.md before
each.

0. **Major-version gate + pre-migration backup** — released on the **1.x line**
   (e.g. v1.6.0) and **confirmed installed at KDPI before any 2.0 release
   exists.** The code that decides what update to offer is the installed 1.x
   code, so the gate must be there first. (See §Release safety and
   [[StudioFire/docs/Release-and-Branches|Release & Branches]].)
1. **Duration audit** (§Durations) — read-only `scripts/duration_audit.py`.
   **Hard stop:** Mark runs it on the playout DB and shares the numbers before
   any duration *fix* is built. The audit's decision table cannot be skipped.
2. **Play-log foundation** — spot `category`/`sponsor`, an artist/album/duration
   snapshot on the queue entry that P1 echoes into `track_start`, and
   `played_sec` computed at ingest.
3. **Reports R0 + R1 + R2 + R3** (§Reports).
4. **Thin music identity** — file tags + an editable station genre list +
   editable **rotation categories/buckets** (Power/Recurrent/Gold/specialty,
   John-editable) + manual/bulk assign + human locks. A **zero-internet** path.
   *Categories are in the MVP; clock/daypart UI is 2.1.*
5. **Duration fixes** (§Durations) — prioritized by the audit: normalize
   0 → NULL, write-back to `tracks`, measure full plays on air. Decode
   measurement runs on the **production PC only**.
6. **Human-reviewed playlist generator** (§Generator), plus
   `docs/Playlist-Generator.md`. Output is a normal playlist John reviews —
   **never generate-to-air.**

**Staged as 2.0.x / 2.1 (NOT 2.0.0):** multi-source enrichment (MusicBrainz /
AcoustID / Last.fm / Deezer), the style layer, chart-derived popularity tiers,
review-queue automation, deep Genres admin, and the clock/daypart UI. The
generator must not block on these.

**Not to be built yet:** the StreamGuys now-playing metadata push. It is an
optional later integration; logging never depends on it.

## Local-first logging principle (non-negotiable)

**Logging and audits are self-contained. StudioFire tracks what airs on its own
and depends on nothing external to do it.** Reports are built from the local play
log. They do not wait on StreamGuys, Icecast or any CDN, and they must keep
working if every outside service is down. StudioFire is the **system of record**
for the air log — not the stream host.

StreamGuys integration (pushing now-playing metadata) is a **later, optional
enhancement — never a dependency for logging.** When it is built (post-2.0.0,
integration phase), P2 may push the current title/artist on each `track_start`;
it must be fire-and-forget and must never sit in the audio path. The open
questions about licensing bodies and StreamGuys' metadata endpoint shape only
that later integration — they **do not gate** R0 or any 2.0.0 item.

## R0 — the local music air-log export

A first-class, **local** export of what aired, shaped for music-licensing
reporting (SoundExchange / PRO-shaped): title, artist, album, ISRC **or**
album + label, start time, `played_sec` / end, and a stable item key per airing;
spin/ATH hooks where the data supports them. CSV export **and** an on-screen
view. Built entirely from the local play log — **no external dependency, no
StreamGuys answer required.** This is the report that lets John hand a licensing
body a defensible air log without waiting on anyone. It ships in the 2.0.0 spine.

The other priority reports: **R1** legal-ID compliance (per clock hour, PASS/MISS
against a configurable window), **R2** underwriting affidavit (sponsor, scheduled
vs aired, printable), **R3** problem tracks / library health (decode errors,
missing files, unknown durations, missing tags). Spot `category`/`sponsor` must
land before R2 is "done," and the affidavit's *scheduled* math is defined from
the spot-rule triggers, not guessed.

## Music identity, durations, generator (summaries)

- **Catalog topology:** enrichment runs **only on the production PC**; the
  catalog is shared to the playout PC via an **atomic NAS snapshot**, never a
  live shared SQLite over SMB. Playout never depends on the catalog; if the
  snapshot is gone it keeps its last merged metadata. Enrichment / internet /
  bulk decode are **hard-refused on the playout role in code**, not just in docs.
- **Durations:** store `duration_source` provenance; trust order
  `manual > decoded ≈ measured_air > header > musicbrainz > lst`. **NULL means
  unknown everywhere; 0/negative are never stored** (a migration converts
  existing `0.0` → NULL). The on-air PC never bulk-decodes over SMB.
- **Generator:** inputs are a saved "recipe" (run time + genre mix + tier mix +
  era + a randomization/temperature slider + a stored seed). Rules live in **one
  module** (`services/core/generator_rules.py`), each a small testable object in a
  `RULES` list (`filter` vs `constraint`, `hard` vs `soft` with `relax_order`).
  Adding a rule = one class + one test + a doc line, no changes to the core
  algorithm. **No auto mode; nothing generated goes to air without passing
  through a normal playlist John reviews.**

## Binding ground rules (every 2.0 change)

- **P1 stdlib-only law.** P1 (the audio engine) stays stdlib-only and must never
  gain a dependency on the network, the NAS catalog, internet lookups, or the DB.
  New P1 behavior is limited to copying extra fields from queue entries into
  journal lines.
- **Additive migrations only** (`CREATE TABLE`, `ADD COLUMN`, `CREATE INDEX`); new
  numbered migration per change, never edit an old one. A 1.x rollback must still
  run against a migrated DB. Old rows / unenriched tracks keep working, with
  NULL-safe reports and UI.
- **Tests alongside each feature**, in the style of the existing `tests/`.
  Migration tests run against **a real station-DB copy** and an empty DB, and
  assert row counts in `tracks`, `playlists`, `playlist_items`, `play_history`
  and `spot_rules` are unchanged.
- **Prefer stdlib** (`urllib`, `json`, `sqlite3`) + the existing `mutagen` so
  `requirements.txt` stays unchanged. A genuinely required new package or `bin/`
  binary (e.g. `fpcalc`) means 2.0 ships via the **full installer**, and the
  major-version notes must say so (`fpcalc` stays optional, production-PC only).

## §6 Release safety (AGREED — ship untouched)

The release-safety design is summarized here and detailed, with the branch model,
in [[StudioFire/docs/Release-and-Branches|Release & Branches]].

- **Updates reach a station only as a published GitHub Release**, cut from `main`
  only. Branches and unreleased commits never reach a station.
- **Major-version gate** (ships FIRST, in a 1.x release, confirmed installed
  before 2.0 exists): the updater lists releases and distinguishes
  `update_available` (newest within the current major — the everyday button)
  from `major_available` (a higher major — never the everyday button). `apply`
  without `--tag` never crosses a major; `apply --tag v2.x` also needs an
  explicit `--major` flag. The Settings UI shows a distinct amber/red card,
  admin-only, requiring the admin to **type the version** and a final confirm,
  behind a pre-flight (disk space, `PRAGMA integrity_check`, not in emergency
  mode, not within 10 min of a show). Nothing major ever auto-installs.
- **Release-channel guard in code** (on `main`): `scripts/release.py` refuses a
  MAJOR-version publish without an explicit `--major` flag. Do **not** pass
  `--major` until the gate is confirmed installed at every station.
- **Database safety:** pre-migration backup via the SQLite backup API +
  `PRAGMA integrity_check` (abort if either fails; keep the last 5). A cross-major
  install also restores the DB on a failed health check. The published catalog is
  `ATTACH`ed **read-only**; catalog edits happen only on the production PC.
- **Indexing safety (on-air PC):** no full re-tag — add a `tags_version` column
  and re-read old rows on a low-priority background pass; new/changed-file
  detection is unchanged; the indexer skips the `.studiofire` snapshot folder;
  no internet lookups or bulk decode in the on-air indexer.
